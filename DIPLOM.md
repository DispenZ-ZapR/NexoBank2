### 1.1. Актуальность разработки банковских систем

**Современные требования к банковским системам:**

- **Безопасность** — защита персональных данных и финансовой информации клиентов
- **Надежность** — обеспечение бесперебойной работы и целостности данных
- **Масштабируемость** — способность обрабатывать растущее количество пользователей и транзакций
- **Производительность** — быстрая обработка операций в режиме реального времени
- **Соответствие стандартам** — выполнение требований регуляторов и международных стандартов

Backend-разработка банковских систем требует применения enterprise-подходов: многоуровневой архитектуры, транзакционности, аудита операций, системы ролей и прав доступа.

**Выбор технологического стека:**

Для разработки банковских систем чаще всего используются языки и платформы, зарекомендовавшие себя в enterprise-сегменте: Java (Spring), C# (.NET), иногда Go. Java и экосистема Spring являются де-факто стандартом для финансовых приложений благодаря:

- Зрелости платформы и богатой экосистеме библиотек

- Высокой производительности и надежности

### 1.2. Обзор используемых технологий

#### 1.2.1. Язык программирования Java

Java — объектно-ориентированный язык программирования общего назначения, созданный компанией Sun Microsystems в 1995 году. Сегодня Java является одним из самых популярных языков для enterprise-разработки.

**Основные характеристики Java:**

- **Платформенная независимость** — принцип "Write Once, Run Anywhere". Java-код компилируется в байт-код, который выполняется на JVM (Java Virtual Machine), доступной для всех основных операционных систем.

- **Объектно-ориентированный подход** — всё в Java является объектом (кроме примитивных типов), что обеспечивает модульность, инкапсуляцию и повторное использование кода.

- **Строгая типизация** — типы переменных определяются при компиляции, что позволяет выявлять ошибки на ранних этапах разработки.

- **Автоматическое управление памятью** — Garbage Collector автоматически освобождает неиспользуемую память, предотвращая утечки.

- **Многопоточность** — встроенная поддержка параллельного выполнения кода для эффективного использования ресурсов.

- **Безопасность** — встроенные механизмы безопасности на уровне языка и платформы.

**Преимущества для банковских систем:**

- Высокая надежность и стабильность
- Отличная производительность
- Богатая экосистема библиотек для работы с базами данных, безопасностью, веб-сервисами
- Большое количество квалифицированных специалистов на рынке труда

В данном проекте используется Java версии 17 (LTS — Long Term Support) — стабильная версия с длительной поддержкой и современными возможностями языка.

#### 1.2.2. Фреймворк Spring Boot

Spring Boot — это фреймворк для упрощенной разработки production-ready приложений на Java с использованием экосистемы Spring Framework.

**Spring Framework** — комплексный фреймворк для Java, предоставляющий инфраструктуру для разработки enterprise-приложений. Основные концепции:

- **Inversion of Control (IoC)** — инверсия управления. Вместо того чтобы объект сам создавал свои зависимости, они "внедряются" извне контейнером Spring.

- **Dependency Injection (DI)** — внедрение зависимостей. Spring автоматически создает объекты (бины) и подставляет их туда, где они нужны, что упрощает тестирование и поддержку кода.

- **Aspect-Oriented Programming (AOP)** — аспектно-ориентированное программирование для разделения сквозной функциональности (логирование, транзакции, безопасность).

**Spring Boot** упрощает настройку Spring-приложений:

- **Автоконфигурация** — Spring Boot автоматически настраивает приложение на основе зависимостей в classpath.

- **Встроенный сервер** — Tomcat встроен по умолчанию, не требуется развертывание на внешний сервер приложений.

- **Starter-зависимости** — предопределенные наборы зависимостей для типичных сценариев (spring-boot-starter-web, spring-boot-starter-data-jpa, spring-boot-starter-security).

- **Production-ready функции** — встроенные endpoints для мониторинга и управления приложением.

**Spring Data JPA** — часть экосистемы Spring для работы с базами данных. JPA (Java Persistence API) — спецификация для ORM (Object-Relational Mapping), позволяющая работать с базой данных через объекты Java вместо SQL-запросов.

В проекте NexoBank2 используется Spring Boot версии 4.0.3 с модулями:
- Spring Web MVC — для создания REST API
- Spring Data JPA — для работы с PostgreSQL
- Spring Security — для аутентификации и авторизации

#### 1.2.3. Spring Security и JWT аутентификация

**Spring Security** — мощный и гибкий фреймворк для обеспечения аутентификации и авторизации в Java-приложениях. Является стандартом безопасности для Spring-приложений.

**Основные возможности:**

- **Аутентификация** — проверка подлинности пользователя (кто вы?)
- **Авторизация** — проверка прав доступа (что вам разрешено делать?)
- **Защита от атак** — CSRF, XSS, Session Fixation и других угроз
- **Интеграция** — поддержка различных методов аутентификации (форма, HTTP Basic, OAuth2, JWT)

**JWT (JSON Web Token)** — открытый стандарт для создания токенов доступа. JWT состоит из трех частей:

1. **Header** — тип токена и алгоритм шифрования
2. **Payload** — данные пользователя (claims)
3. **Signature** — цифровая подпись для проверки подлинности

**Преимущества JWT для REST API:**

- **Stateless** — сервер не хранит сессии, токен содержит всю необходимую информацию
- **Масштабируемость** — легко масштабировать горизонтально, так как нет привязки к серверу
- **Кроссплатформенность** — токен можно использовать в веб, мобильных и десктоп приложениях
- **Безопасность** — токен подписан и может быть зашифрован

**Процесс аутентификации в NexoBank2:**

1. Пользователь отправляет email и пароль на `/api/auth/login`
2. Сервер проверяет учетные данные
3. При успехе генерируется JWT токен с информацией о пользователе
4. Клиент сохраняет токен и отправляет его в заголовке `Authorization: Bearer <token>` при каждом запросе
5. JwtFilter проверяет токен и извлекает информацию о пользователе
6. Spring Security проверяет права доступа к запрашиваемому ресурсу

**Процесс регистраций нового клиента в NexoBank2:**
1. Сотрудник отправляет POST-запрос на /api/client/save с JSON-телом, содержащим:

- `email` — электронная почта клиента

- `phoneNumber` — номер телефона в формате +996XXXXXXXXX

- `firstName, lastName, middleName` — ФИО

- `dateOfBirth` — дата рождения

- `personalNumber` — ИНН (14 цифр)

- `passportNumber` — номер паспорта в формате AN1234567
2. Система валидирует входные данные (формат email, паспорта, ИНН и т.д.)
3. Создаётся запись пользователя (User) с типом CLIENT
4. Создаётся запись клиента (Client) со статусом UNVERIFIED и кредитным рейтингом 0
5. Публикуется событие ClientCreatedEvent для создания паспортных данных
6. На email клиента отправляется письмо со ссылкой для подтверждения аккаунта и установки пароля
7. Клиент переходит по ссылке /api/user/verify/{token} и устанавливает пароль — статус меняется на ACTIVE

**Процесс регистрации нового сотрудника в NexoBank2:**
1. Администратор отправляет POST-запрос на /api/employees/save с JSON-телом, содержащим те же персональные данные, что и для клиента, плюс:

- `positionId` — ID должности сотрудника

- `salary` — заработная плата
2. Система валидирует данные и проверяет существование должности в базе
3. Создаётся запись пользователя (User), привязывается к сотруднику
4. Создаётся запись сотрудника (Employee) со статусом UNVERIFIED, фиксируется дата найма (hiredAt)
5. На email сотрудника отправляется письмо со ссылкой для подтверждения аккаунта и установки пароля
6. После перехода по ссылке сотрудник устанавливает пароль и получает доступ к системе
#### 1.2.4. PostgreSQL как система управления базами данных
**PostgreSQL** — мощная объектно-реляционная система управления базами данных (СУБД) с открытым исходным кодом. Является одной из самых продвинутых СУБД в мире.

**Характеристики PostgreSQL:**

- **ACID-совместимость** — гарантирует атомарность, согласованность, изолированность и долговечность транзакций
- **Расширенные типы данных** — поддержка JSON, массивов, геоданных, UUID и других типов
- **Производительность** — эффективная обработка сложных запросов и больших объемов данных
- **Надежность** — проверенная временем стабильность и целостность данных
- **Расширяемость** — возможность создания собственных типов данных, функций и расширений

**Преимущества для банковских систем:**

- Строгая типизация и проверка ограничений целостности
- Поддержка сложных транзакций с высоким уровнем изоляции
- MVCC (Multi-Version Concurrency Control) для эффективной работы с конкурентными запросами
- Репликация и резервное копирование для обеспечения отказоустойчивости
- Бесплатная лицензия для коммерческого использования

В проекте NexoBank2 PostgreSQL используется для хранения всех данных: пользователей, счетов, транзакций, операций.

#### 1.2.5. Flyway для управления миграциями

**Flyway** — инструмент для управления версиями базы данных (Database Migration Tool). Позволяет отслеживать, версионировать и применять изменения схемы базы данных.

**Проблема, которую решает Flyway:**

При разработке приложения структура базы данных постоянно меняется (добавляются таблицы, колонки, индексы). Вручную применять эти изменения на разных средах (разработка, тестирование, продакшн) — ошибкоемко и неэффективно.

**Как работает Flyway:**

1. SQL-файлы миграций помещаются в папку `src/main/resources/db/migration`
2. Имена файлов следуют шаблону: `V{версия}__{описание}.sql` (например, `V1__Create_base_tables.sql`)
3. При запуске приложения Flyway проверяет, какие миграции уже выполнены (хранит историю в таблице `flyway_schema_history`)
4. Новые миграции применяются автоматически в порядке версий

**Преимущества:**

- Версионирование схемы базы данных вместе с кодом
- Автоматическое применение изменений при развертывании
- Консистентность между средами разработки
- Возможность отката изменений (с помощью undo-миграций)
- Аудит всех изменений схемы

В NexoBank2 используется одна миграция `V1__Create_base_tables.sql`, которая создает все таблицы, индексы и ограничения целостности.

#### 1.2.6. MapStruct для маппинга объектов

**MapStruct** — генератор кода для маппинга между Java bean объектами. Решает проблему преобразования между сущностями (Entity) и DTO (Data Transfer Objects).

**Проблема:**

В enterprise-приложениях используется паттерн DTO — объекты для передачи данных между слоями. Сущности базы данных (Entity) не должны напрямую возвращаться клиенту, так как:
- Могут содержать служебную информацию
- Могут вызвать проблемы с ленивой загрузкой (LazyInitializationException)
- Нарушают принцип разделения ответственности

Вручную писать код преобразования между Entity и DTO — утомительно и подвержено ошибкам.

**Решение MapStruct:**

MapStruct генерирует код маппинга на этапе компиляции на основе интерфейсов с аннотациями:

```java
@Mapper(componentModel = "spring")
public interface ClientMapper {
    ClientResponse toResponse(Client client);
    Client toEntity(ClientRequest request);
}
```

**Преимущества:**

- Высокая производительность (код генерируется при компиляции, без рефлексии)
- Типобезопасность (ошибки выявляются на этапе компиляции)
- Простота использования
- Автоматическая интеграция со Spring

В NexoBank2 используются маперы для всех сущностей: ClientMapper, AccountMapper, OperationMapper и другие.

#### 1.2.7. Документирование API (Swagger )

**Swagger (OpenAPI)** — набор инструментов для проектирования, документирования и тестирования REST API.

**Springdoc OpenAPI** — библиотека для автоматической генерации документации API в Spring Boot приложениях.

**Что предоставляет:**

- **Swagger UI** — интерактивная веб-страница (`/swagger-ui.html`) с документацией всех endpoints, моделей данных, возможностью выполнять тестовые запросы прямо в браузере.

- **OpenAPI Specification** — JSON/YAML описание API по стандарту OpenAPI 3.0, которое можно импортировать в другие инструменты (Postman, генераторы клиентского кода).

- **Аннотации** — `@Operation`, `@Tag`, `@Parameter`, `@Schema` для расширения автоматически генерируемой документации.

**Преимущества для проекта:**

- Наглядная демонстрация API для заказчиков и разработчиков
- Возможность тестировать API без дополнительных инструментов
- Автоматическая синхронизация документации с кодом
- Профессиональный подход к документированию

В NexoBank2 доступен интерфейс:
- Swagger UI: `http://localhost:8080/swagger-ui.html`

### 1.3. Архитектурные паттерны enterprise-приложений

Enterprise-приложения требуют применения проверенных архитектурных паттернов для обеспечения масштабируемости, поддерживаемости и тестируемости.

**Многоуровневая архитектура (Layered Architecture):**

Приложение разделяется на слои с четким разделением ответственности:

1. **Presentation Layer (Контроллеры)** — обработка HTTP-запросов, валидация входных данных, формирование ответов
2. **Business Logic Layer (Сервисы)** — бизнес-логика, координация операций, управление транзакциями
3. **Data Access Layer (Репозитории)** — доступ к базе данных, выполнение CRUD-операций
4. **Domain Layer (Сущности)** — модели предметной области

**Паттерн DTO (Data Transfer Object):**

Используется для передачи данных между слоями. DTO содержат только необходимые данные без бизнес-логики.

**Преимущества:**
- Скрывает внутреннюю структуру сущностей
- Позволяет возвращать только нужные поля
- Предотвращает проблемы с ленивой загрузкой

**Паттерн Repository:**

Абстрагирует логику доступа к данным. Репозиторий предоставляет коллекцию-подобный интерфейс для работы с сущностями.

**Паттерн Service:**

Инкапсулирует бизнес-логику приложения. Сервисы координируют работу нескольких репозиториев, управляют транзакциями.

**Транзакционность:**

Критически важна для банковских систем. Аннотация `@Transactional` обеспечивает:
- Атомарность — либо все операции выполняются, либо ни одна
- Согласованность — данные остаются в корректном состоянии
- Изолированность — транзакции не влияют друг на друга
- Долговечность — результаты сохраняются даже при сбоях

### 1.4. REST API и принципы проектирования

**REST (Representational State Transfer)** — архитектурный стиль для проектирования распределенных систем.

**Принципы REST:**

1. **Клиент-сервер** — разделение интерфейса и хранения данных
2. **Stateless** — каждый запрос содержит всю необходимую информацию
3. **Кэширование** — ответы могут кэшироваться для повышения производительности
4. **Единообразие интерфейса** — стандартизированные методы взаимодействия
5. **Слоистая система** — клиент не знает, с каким слоем взаимодействует

**HTTP-методы в REST:**

| Метод | Действие | Идемпотентность | Пример |
|-------|----------|-----------------|--------|
| GET | Получение данных | Да | `GET /api/accounts` |
| POST | Создание ресурса | Нет | `POST /api/clients` |
| PUT | Полное обновление | Да | `PUT /api/clients/1` |
| PATCH | Частичное обновление | Нет | `PATCH /api/clients/1/email` |
| DELETE | Удаление ресурса | Да | `DELETE /api/clients/1` |

**Коды ответов HTTP:**

- **2xx Success** — успешное выполнение (200 OK, 201 Created, 204 No Content)
- **4xx Client Error** — ошибка клиента (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found)
- **5xx Server Error** — ошибка сервера (500 Internal Server Error)

**Best Practices REST API:**

- Использование существительных в URL (`/api/accounts`, а не `/api/getAccounts`)
- Версионирование API (`/api/v1/accounts`)
- Фильтрация и пагинация для списков (`/api/accounts?page=0&size=10`)
- Использование правильных HTTP-кодов ответа
- Документирование API (Swagger/OpenAPI)
- Обработка ошибок с понятными сообщениями

### 2.3. Проектирование базы данных

Проектирование базы данных — критически важный этап разработки банковской системы. От правильности структуры зависит целостность данных, производительность и возможность масштабирования.

**Анализ предметной области:**

В процессе анализа были выделены следующие основные сущности:

1. **Passport (Паспорт)** — документ, удостоверяющий личность. Содержит ФИО, дату рождения, серию и номер паспорта, ИНН.

2. **User (Пользователь)** — базовая сущность для всех пользователей системы. Содержит email, пароль, тип пользователя (CLIENT/EMPLOYEE/ADMIN), привязку к паспорту.

3. **Client (Клиент)** — физическое лицо, использующее банковские услуги. Имеет кредитный рейтинг, статус (ACTIVE/BLOCKED/DELETED).

4. **Employee (Сотрудник)** — работник банка. Имеет зарплату, дату найма, статус (ACTIVE/FIRED).

5. **EmployeePosition (Должность)** — справочник должностей (Менеджер, Кассир, Администратор).

6. **EmployeePositionsMap** — связь многие-ко-многим между сотрудниками и должностями.

7. **AccountType (Тип счета)** — справочник типов счетов (Текущий, Сберегательный, Депозитный).

8. **AccountCurrency (Валюта)** — справочник валют (KGS, USD, EUR, RUB) с кодами и цифровыми кодами.

9. **Account (Счет)** — банковский счет клиента. Содержит номер счета, баланс, валюту, тип, статус (ACTIVE/FROZEN/CLOSED).

10. **AccountRequest (Заявка на счет)** — заявка клиента на открытие нового счета. Содержит статус (PENDING/APPROVED/REJECTED), информацию об одобрившем сотруднике.

11. **Operation (Операция)** — запись о банковской операции. Содержит инициатора, канал (WEB/MOBILE/ATM), статус, причину.

12. **Transaction (Транзакция)** — конкретное движение средств по счету. Связана с операцией, содержит тип (DEBIT/CREDIT), сумму, баланс после транзакции.

- **Employee → AccountRequest (1:M)** — сотрудник может одобрить много заявок

**Ключевые особенности схемы:**

1. **Нормализация** — база данных находится в 3НФ (третьей нормальной форме), что исключает избыточность данных.

2. **Ограничения целостности** — внешние ключи с каскадным удалением обеспечивают целостность данных.

3. **Индексы** — созданы индексы на часто используемые поля (email, phone_number, account_number) для ускорения поиска.

4. **Уникальные ограничения** — email и phone_number уникальны среди активных пользователей (deleted_at IS NULL).

5. **Мягкое удаление** — поле deleted_at позволяет "удалять" пользователей без физического удаления из БД.

6. **UUID для операций** — использование UUID вместо BIGINT для операций обеспечивает глобальную уникальность.

**Поток обработки запроса (на примере перевода денег):**

1. **Клиент** отправляет POST запрос на `/api/operations/transfer` с JWT токеном в заголовке Authorization

2. **JwtFilter** перехватывает запрос, проверяет токен, извлекает информацию о пользователе, устанавливает Authentication в SecurityContext

3. **Spring Security** проверяет права доступа к endpoint (требуется роль CLIENT)

4. **OperationController** принимает запрос:
   - Валидирует входные данные (@Valid TransactionRequest)
   - Извлекает текущего пользователя из SecurityContext
   - Вызывает OperationService.transfer()

5. **OperationService** выполняет бизнес-логику:
   - Проверяет, что счет отправителя принадлежит пользователю
   - Проверяет достаточность средств
   - Создает запись Operation со статусом PENDING
   - Вызывает AccountService.transfer() для списания/зачисления
   - Вызывает TransactionService.record() для записи транзакций
   - Обновляет статус Operation на SUCCESSFULLY или FAILED
   - Все операции выполняются в одной транзакции (@Transactional)

6. **AccountService** обновляет балансы счетов

7. **TransactionService** создает записи транзакций (DEBIT и CREDIT)

8. **Repositories** выполняют SQL запросы через JPA

9. **PostgreSQL** сохраняет изменения

10. **Ответ** возвращается обратно по цепочке: Service → Controller → Client

**Преимущества архитектуры:**

- **Разделение ответственности** — каждый слой решает свою задачу
- **Тестируемость** — слои можно тестировать изолированно с моками
- **Поддерживаемость** — изменения в одном слое не затрагивают другие
- **Масштабируемость** — можно заменить реализацию слоя (например, сменить БД)
- **Безопасность** — централизованная обработка аутентификации и авторизации

### 2.6. Описание реализованного функционала

#### 2.6.1. Система аутентификации и авторизации

Система безопасности построена на Spring Security с использованием JWT токенов для stateless аутентификации.

**API Endpoints:**

| Метод | URL | Описание | Доступ |
|-------|-----|----------|--------|
| POST | `/api/clients` | Регистрация клиента | Публичный |
| POST | `/api/auth/login` | Вход в систему | Публичный |
| GET | `/api/auth/activate` | Активация аккаунта | Публичный |

**Процесс регистрации клиента:**

1. Клиент отправляет POST запрос с данными:
   - Паспортные данные (ФИО, дата рождения, номер паспорта, ИНН)
   - Email и номер телефона
   - Пароль

2. Система проверяет:
   - Уникальность email и номера телефона
   - Уникальность номера паспорта
   - Валидность данных (@Valid аннотации)

3. Создаются записи:
   - Passport — паспортные данные
   - User — учетная запись с хешированным паролем
   - Client — профиль клиента

4. Генерируется токен активации и отправляется на email

5. Возвращается ответ с информацией о клиенте

**Процесс входа в систему:**

1. Клиент отправляет email и пароль

2. Spring Security через UserDetailService загружает пользователя из БД

3. Проверяется пароль с использованием BCryptPasswordEncoder

4. При успехе JwtService генерирует JWT токен:
   - Subject: user ID
   - Claims: email, user type, roles
   - Expiration: настраивается через JWT_TOKEN_TIME

5. Токен возвращается клиенту в формате:
```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

**Процесс авторизации запросов:**

1. Клиент отправляет запрос с заголовком:
```
Authorization: Bearer <JWT_TOKEN>
```

2. JwtFilter перехватывает запрос:
   - Извлекает токен из заголовка
   - Валидирует токен (подпись, срок действия)
   - Извлекает user ID из токена
   - Загружает пользователя из БД
   - Создает Authentication объект
   - Устанавливает в SecurityContext

3. Spring Security проверяет права доступа на основе ролей

**Особенности реализации:**

- Пароли хешируются с использованием BCrypt (необратимое шифрование)
- JWT токены подписываются секретным ключом (HMAC-SHA256)
- Токены имеют ограниченный срок действия (по умолчанию 1 час)
- Система активации через email предотвращает регистрацию с чужими адресами

#### 2.6.3. Управление банковскими счетами

**API Endpoints:**

| Метод | URL | Описание | Роль |
|-------|-----|----------|------|
| GET | `/api/accounts` | Мои счета | CLIENT |
| GET | `/api/accounts/{id}` | Информация о счете | CLIENT (владелец) |
| POST | `/api/accounts/freeze/{id}` | Заморозить счет | EMPLOYEE |
| POST | `/api/accounts/unblock/{id}` | Разблокировать счет | EMPLOYEE |
| GET | `/api/accounts/{id}/balance` | Баланс счета | CLIENT (владелец) |

**Типы счетов:**

1. **Текущий счет** — для повседневных операций
2. **Сберегательный счет** — для накоплений
3. **Депозитный счет** — срочный вклад

**Поддерживаемые валюты:**

- KGS (Кыргызский сом) — код 417
- USD (Доллар США) — код 840
- EUR (Евро) — код 978
- RUB (Российский рубль) — код 643

**Статусы счета:**

- **ACTIVE** — активный, доступны все операции
- **FROZEN** — заморожен, операции запрещены
- **CLOSED** — закрыт, восстановление невозможно

**Генерация номера счета:**

Номер счета генерируется автоматически по формуле:
```
YYYYMMDDXXXXXXXX
где:
YYYY — год
MM — месяц
DD — день
XXXXXXXX — случайное 8-значное число
```

Пример: `20250115123456789`

**Особенности:**

- Счет создается только через систему заявок (AccountRequest)
- Клиент не может самостоятельно заморозить/закрыть счет
- При блокировке счета все операции по нему запрещаются
- Баланс хранится с точностью до 4 знаков после запятой (DECIMAL 19,4)

#### 2.6.4. Система денежных переводов

Ключевой функционал банковской системы — выполнение денежных переводов с гарантией транзакционной целостности.

**API Endpoint:**

```
POST /api/operations/transfer
```

**Тело запроса:**

```json
{
  "fromAccountId": 1,
  "toAccountId": 2,
  "amount": 1000.50,
  "reason": "Оплата за услуги"
}
```

**Алгоритм выполнения перевода:**

1. **Проверка прав доступа**
   - Счет отправителя должен принадлежать текущему пользователю
   - Нельзя переводить на тот же счет

2. **Создание операции**
   - Создается запись Operation со статусом PENDING
   - Фиксируется инициатор, канал (WEB), причина, время

3. **Выполнение перевода** (в одной транзакции)
   - Проверка достаточности средств на счете отправителя
   - Проверка статуса счетов (оба должны быть ACTIVE)
   - Списание суммы со счета отправителя
   - Зачисление суммы на счет получателя

4. **Запись транзакций**
   - Создается DEBIT транзакция (списание) для счета отправителя
   - Создается CREDIT транзакция (зачисление) для счета получателя
   - В каждой транзакции фиксируется баланс после операции

5. **Обновление статуса операции**
   - При успехе: SUCCESSFULLY
   - При ошибке: FAILED (с откатом всех изменений)

**Гарантии транзакционности:**

Аннотация `@Transactional` обеспечивает:
- **Атомарность** — либо выполняются все шаги, либо ни один
- **Согласованность** — сумма списания равна сумме зачисления
- **Изолированность** — параллельные переводы не влияют друг на друга
- **Долговечность** — результат сохраняется даже при сбое сервера

**Обработка ошибок:**

- `BadRequestException` — недостаточно средств, счет заблокирован
- `NotFoundException` — счет не найден
- `ForbiddenException` — попытка перевода с чужого счета
- `ServerErrorException` — ошибка базы данных

**История операций:**

```
GET /api/operations/my — мои операции
GET /api/operations/{uuid} — детали операции с транзакциями
```

#### 2.6.5. Обработка заявок на открытие счетов

Система заявок реализует процесс одобрения открытия новых счетов сотрудниками банка.

**API Endpoints:**

| Метод | URL | Описание | Роль |
|-------|-----|----------|------|
| POST | `/api/account-requests` | Создать заявку | CLIENT |
| GET | `/api/account-requests` | Список заявок | EMPLOYEE |
| GET | `/api/account-requests/my` | Мои заявки | CLIENT |
| POST | `/api/account-requests/{id}/approve` | Одобрить | EMPLOYEE |
| POST | `/api/account-requests/{id}/reject` | Отклонить | EMPLOYEE |

**Процесс создания заявки:**

1. Клиент указывает:
   - Тип счета (текущий/сберегательный/депозитный)
   - Валюту (KGS/USD/EUR/RUB)

2. Создается запись AccountRequest со статусом PENDING

3. Заявка попадает в очередь на рассмотрение сотрудниками

**Процесс одобрения:**

1. Сотрудник просматривает заявку

2. При одобрении:
   - Создается новый счет (Account)
   - Генерируется уникальный номер счета
   - Устанавливается начальный баланс 0
   - Статус счета: ACTIVE
   - Заявка переводится в статус APPROVED
   - Фиксируется ID одобрившего сотрудника и время обработки

3. Клиент получает уведомление (опционально через email)

**Процесс отклонения:**

1. Сотрудник указывает причину отклонения

2. Заявка переводится в статус REJECTED

3. Причина сохраняется в поле rejection_reason

**Статусы заявки:**

- **PENDING** — ожидает рассмотрения
- **APPROVED** — одобрена, счет создан
- **REJECTED** — отклонена

**Особенности:**

- Клиент может создавать неограниченное количество заявок
- Одна заявка = один счет
- Нельзя повторно обработать уже обработанную заявку
- История заявок сохраняется для аудита

#### 2.7.3. Сервис с транзакционной логикой перевода

```java
@Service
@AllArgsConstructor
public class OperationServiceImpl implements OperationService {
    
    private final OperationRepository operationRepository;
    private final AccountRepository accountRepository;
    private final AccountService accountService;
    private final TransactionService transactionService;

    @Override
    @Transactional
    public Operation transfer(TransactionRequest request, User initiator) {
        // Загрузка счетов с проверкой существования
        Account fromAccount = accountRepository
            .findByIdWithClientAndUser(request.getFromAccountId())
            .orElseThrow(() -> new NotFoundException("Счёт отправителя не найден"));
        
        Account toAccount = accountRepository
            .findById(request.getToAccountId())
            .orElseThrow(() -> new NotFoundException("Счёт получателя не найден"));

        // Проверка прав доступа
        if (!fromAccount.getClient().getUser().getId().equals(initiator.getId())) {
            throw new BadRequestException(
                "Счёт отправителя не принадлежит вам");
        }
        
        // Проверка на перевод самому себе
        if (request.getFromAccountId().equals(request.getToAccountId())) {
            throw new BadRequestException("Нельзя переводить на тот же счет");
        }

        // Создание операции со статусом PENDING
        Operation operation = new Operation();
        operation.setInitiator(initiator);
        operation.setChannel("WEB");
        operation.setStatus(OperationStatus.PENDING);
        operation.setReason(request.getReason());
        operation.setCreatedAt(LocalDateTime.now());
        operation = operationRepository.save(operation);

        try {
            // Выполнение перевода (списание и зачисление)
            accountService.transfer(
                request.getFromAccountId(), 
                request.getToAccountId(), 
                request.getAmount()
            );
            
            // Перезагрузка счетов с обновленными балансами
            fromAccount = accountRepository.findById(request.getFromAccountId()).get();
            toAccount = accountRepository.findById(request.getToAccountId()).get();
            
            // Запись транзакций
            transactionService.record(fromAccount, toAccount, 
                                     request.getAmount(), operation);

            // Обновление статуса на успешный
            operation.setStatus(OperationStatus.SUCCESSFULLY);
            operationRepository.save(operation);

            return operation;
            
        } catch (BadRequestException | NotFoundException e) {
            // Бизнес-ошибки (недостаточно средств, счет заблокирован)
            operation.setStatus(OperationStatus.FAILED);
            operationRepository.save(operation);
            throw e;
        } catch (DataAccessException e) {
            // Ошибки базы данных
            operation.setStatus(OperationStatus.FAILED);
            operationRepository.save(operation);
            throw new ServerErrorException("Ошибка БД: " + e.getMessage());
        } catch (RuntimeException e) {
            // Прочие ошибки
            operation.setStatus(OperationStatus.FAILED);
            operationRepository.save(operation);
            throw new ServerErrorException("Ошибка перевода: " + e.getMessage());
        }
    }
}
```

**Ключевые моменты:**

- `@Transactional` — все операции выполняются в одной транзакции
- При любой ошибке происходит откат (rollback) всех изменений
- Статус операции всегда обновляется (SUCCESSFULLY или FAILED)
- Обработка разных типов исключений с соответствующими сообщениями

#### 2.7.5. JWT Service для работы с токенами

```java
@Service
public class JwtService {

    @Value("${jwt.secret.key}")
    private String secretKey;

    @Value("${jwt.token.time}")
    private Long tokenTime;

    // Генерация JWT токена
    public String generateToken(User user) {
        return Jwts.builder()
            .subject(user.getId().toString())
            .claim("email", user.getEmail())
            .claim("userType", user.getUserType().name())
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + tokenTime))
            .signWith(getSigningKey())
            .compact();
    }

    // Извлечение user ID из токена
    public Long extractUserId(String token) {
        String subject = extractClaims(token).getSubject();
        return Long.parseLong(subject);
    }

    // Валидация токена
    public boolean isTokenValid(String token) {
        try {
            extractClaims(token);
            return !isTokenExpired(token);
        } catch (JwtException e) {
            return false;
        }
    }

    // Проверка срока действия
    private boolean isTokenExpired(String token) {
        return extractClaims(token)
            .getExpiration()
            .before(new Date());
    }

    // Извлечение claims из токена
    private Claims extractClaims(String token) {
        return Jwts.parser()
            .verifyWith(getSigningKey())
            .build()
            .parseSignedClaims(token)
            .getPayload();
    }

    // Получение ключа подписи
    private SecretKey getSigningKey() {
        byte[] keyBytes = Decoders.BASE64.decode(secretKey);
        return Keys.hmacShaKeyFor(keyBytes);
    }
}
```

**Пояснения:**

- Токен подписывается секретным ключом (HMAC-SHA256)
- В payload токена сохраняется ID, email и тип пользователя
- Токен имеет ограниченный срок действия
- Валидация проверяет подпись и срок действия

    private final UserDetailService userDetailService;

    public SecurityFilterChain securityFilterChain(HttpSecurity http)

            .csrf(AbstractHttpConfigurer::disable)

                .requestMatchers("/swagger-ui/**", "/v3/api-docs/**",

                .requestMatchers("/api/employees/**").hasRole("EMPLOYEE")
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            )
            .authenticationProvider(authenticationProvider())
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }

        DaoAuthenticationProvider provider = new DaoAuthenticationProvider();
        provider.setUserDetailsService(userDetailService);
        provider.setPasswordEncoder(passwordEncoder());
        return provider;

    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    public AuthenticationManager authenticationManager(
            AuthenticationConfiguration config) throws Exception {
        return config.getAuthenticationManager();
    }
}

### A.4. JWT Filter (JwtFilter.java)

```java
@Component
@RequiredArgsConstructor
public class JwtFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailService userDetailService;

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain) throws ServletException, IOException {
        
        String authHeader = request.getHeader("Authorization");
        
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        String token = authHeader.substring(7);
        
        try {
            if (jwtService.isTokenValid(token)) {
                Long userId = jwtService.extractUserId(token);
                UserDetails userDetails = userDetailService.loadUserById(userId);
                
                UsernamePasswordAuthenticationToken authentication =
                    new UsernamePasswordAuthenticationToken(
                        userDetails, null, userDetails.getAuthorities()
                    );
                
                SecurityContextHolder.getContext()
                    .setAuthentication(authentication);
            }
        } catch (Exception e) {
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            return;
        }
        
        filterChain.doFilter(request, response);
    }
}
```

-- Создание последовательностей для ID
CREATE SEQUENCE public.users_id_seq START WITH 1 INCREMENT BY 1;
CREATE SEQUENCE public.passport_id_seq START WITH 1 INCREMENT BY 1;
CREATE SEQUENCE public.client_id_seq START WITH 1 INCREMENT BY 1;
CREATE SEQUENCE public.account_id_seq START WITH 1 INCREMENT BY 1;

-- Таблица паспортов
CREATE TABLE public.passport (
    id bigint NOT NULL DEFAULT nextval('public.passport_id_seq'),
    first_name varchar(15) NOT NULL,
    last_name varchar(30) NOT NULL,
    middle_name varchar(30),
    date_of_birth date NOT NULL,
    personal_number varchar(255) NOT NULL,
    is_lost boolean DEFAULT false NOT NULL,
    passport_number varchar(255) NOT NULL UNIQUE,
    PRIMARY KEY (id)
);

-- Таблица пользователей
CREATE TABLE public.users (
    id bigint NOT NULL DEFAULT nextval('public.users_id_seq'),
    passport_id bigint NOT NULL UNIQUE,
    password_hash varchar(255),
    email varchar(35) NOT NULL,
    user_type varchar(20) NOT NULL,
    created_at timestamp with time zone NOT NULL,
    phone_number varchar(20) NOT NULL,
    deleted_at timestamp with time zone,
    ac_token varchar,
    activation_token_expires_at timestamp with time zone,
    PRIMARY KEY (id),
    CONSTRAINT users_passport_id_fkey 
        FOREIGN KEY (passport_id) REFERENCES public.passport(id)
);

-- Таблица клиентов
CREATE TABLE public.client (
    id bigint NOT NULL DEFAULT nextval('public.client_id_seq'),
    user_id bigint NOT NULL UNIQUE,
    created_at timestamp with time zone NOT NULL,
    credit_rating integer DEFAULT 0,
    client_status varchar(15) DEFAULT 'ACTIVE' NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT client_user_id_fkey 
        FOREIGN KEY (user_id) REFERENCES public.users(id)
);

-- Индексы для оптимизации
CREATE INDEX idx_users_email ON public.users(email);
CREATE INDEX idx_users_phone_number ON public.users(phone_number);
CREATE UNIQUE INDEX users_email_active_idx 
    ON public.users(email) WHERE (deleted_at IS NULL);
CREATE UNIQUE INDEX users_phone_active_idx 
    ON public.users(phone_number) WHERE (deleted_at IS NULL);
